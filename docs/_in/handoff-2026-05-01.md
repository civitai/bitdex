## 5. The HTTP gap — last real performance blocker

**Reproducer (Justin, end of session):** client saw 15.91s POST `/api/indexes/civitai/query`, server header `x-bitdex-duration-us=2293` (2.3ms engine).

**Confirmed real, not a measurement artifact.** From prod metrics at session end:
- `bitdex_query_duration_seconds`: 0 queries > 5s, 0 > 10s
- `bitdex_http_response_seconds{path="/api/indexes/*/civitai", method="POST"}`: 130 queries > 5s, 61 > 10s, sustained
- The gap = 13s+ outside the engine timer

**Hypothesis:** tokio worker starvation. Pod runs `#[tokio::main(flavor = "multi_thread")]` with default workers (~4 cores given pod CPU req). Handler calls `block_in_place(|| engine.execute_query_traced(...))` which converts an async worker into a blocking worker. Replacement spawns are not instant. Plus doc fetch via `spawn_blocking`. With shadow ON, dual-firing requests + bursts → all 4 async workers can be doing block_in_place simultaneously → new HTTP requests sit in the tokio task queue. `queries_in_flight_peak = 208` confirms the burst geometry.

**v195 unlocks attribution.** Once deployed, slow queries will record:
- `to_handler_us` — **this is the candidate for the 13s gap.** If it's seconds while engine_us is millis, tokio queue is the bottleneck.
- `to_engine_us` — body parse, prefilter substitution
- `engine_us` — current `x-bitdex-duration-us`
- `doc_fetch_us` — `spawn_blocking` doc fetch (also has its own queue-wait component — see §7)
- `to_response_us` — response write

**If `to_handler_us` is the gap, fixes worth considering:**
- Bump tokio worker_threads explicitly (currently default num_cpus). Setting to 16 with 4 CPU cores is fine — workers steal-park.
- Replace `block_in_place` with `spawn_blocking + .await` on the engine call (different starvation profile).
- Drop the shadow comparator's per-request dual-fire if it's the burst source.

## 6. Outstanding work that didn't ship tonight

### sortAtUnix bug — workaround in place, code fix deferred

Bug: `Gte("sortAtUnix", X)` silently returns all rows. Root cause: field is in `time_buckets.filter_field` but not in `filter_fields`, so executor's `range_scan` returns `FieldNotFound`, and `slot_matches_clause` defensive `None => true` branch (`unified_cache.rs:2129`) passes everything.

**Justin's call:** do NOT register sortAtUnix as a regular filter field — too noisy at 100M+ seconds-resolution records. Use the pre-computed time buckets (`24h` / `7d` / `30d` / `1y`).

**Fredrick (model-share) audit done.** Only one bitdex-side filter callsite uses sortAtUnix Gte: `src/server/services/image.service.ts:3321`. Currently broken-but-returns-everything. **This still needs to flip to use `Bucket` filter.** Mailed Fredrick the change-of-plan early in the session — confirm he picked it up tomorrow, or send a follow-up.

**Defensive code fix worth doing:** `unified_cache.rs:2129` `None => true` and `executor.rs FieldNotFound` on range clauses should HARD ERROR (or return empty), not silently pass-all. Otherwise the same bug class is invisible. This is `~30 lines` of code change. Could ship as v196.

### v195 cache parallelization (rayon par_iter)

I had a fork queued for parallelizing `evaluate_filter_work` / `evaluate_sort_work` / `apply_maintenance_results` via rayon. Marked deferred at end-of-session — diminishing returns now that cache_worker isn't blocked. Worth profiling first:

- Worker cycles 24/min, no shed

If profiling shows cycle is the bottleneck again (e.g. when entries grow toward 250K cap), revisit. The shape of the work:
- `unified_cache.rs::evaluate_filter_work` and `evaluate_sort_work` already share precomputed `reconstruct_value` results — outer per-item loop is parallel-safe with `par_iter`

The docstore investigation report at `docs/_in/docstore-p99-investigation-2026-04-30.md` flagged:

**H1 (highest probability):** `spawn_blocking` pool backlog. Smoking gun trace: `docs_us: 251393, docs_count: 0` — 251ms returning zero docs. Only way that happens is queue wait. The `docs_us` timer starts BEFORE `spawn_blocking` enqueue (server.rs:2884) but `bitdex_docstore_read_seconds` histogram fires INSIDE the closure. Histogram looks fine while `docs_us` captures full queue-wait time.

**H2 (medium):** outer `parking_lot::RwLock<DocStoreV3>` writer-priority stall. Flush thread calls `docstore.write().put_batch()` ~every 100ms; fair write-priority queues all subsequent reads.

## 9. New metrics to watch on v195 (post-deploy)

The diagnostic chain expanded substantially. Look for:

| Metric | What it tells us |
|---|---|
| `bitdex_cache_worker_cycle_seconds_bucket` | Worker cycle distribution. Expect p99 < 1s sustained. If p99 climbs near 10s, the budget is too tight for write volume — bump or shed earlier. |
| `bitdex_cache_entries_needs_rebuild` | Live shed backlog. Should hover near 0 in steady state. Spikes = burst write activity, drains = healthy. |
| `bitdex_cache_marked_for_rebuild_total{reason}` | Where shed events come from. `deadline` = budget hit. `count_budget` = legacy fallback (mostly 0 with ms budget). `alive_change` = delete burst. `filter_invalidation` = compound clause stale. `backlog_drop` = worker overwhelmed (concerning if >0). |
| `bitdex_cache_rebuild_completed_total` | Rate of recovery. Should track marked_for_rebuild closely (no growing backlog). |
| `bitdex_http_handler_phase_seconds_bucket{phase=...}` | HTTP gap attribution. **`to_handler` = the smoking gun for tokio queue starvation.** |
