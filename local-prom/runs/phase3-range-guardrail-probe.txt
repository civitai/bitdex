## Simulated Integration Probe

Scenario: A postId field (22.5M entries) with max_range_scan_values: Some(10_000)
receives a range query Gt(postId, 1000).

Expected: QueryTooExpensive error returned immediately, no bitmap work done.
Metric: bitdex_range_scan_rejected_total{field="postId"} incremented by 1.

Config example (civitai-index.json):
{
  "filter_fields": [
    {
      "name": "postId",
      "field_type": "single_value",
      "per_value_lazy": true,
      "max_range_scan_values": 10000
    }
  ]
}

The guardrail check happens before value_to_bitmap_key() conversion, so
no work is done when the cap is exceeded. The loaded_value_count() call
is a single RwLock::read() + HashMap::len() — O(1), negligible overhead
on the normal (non-rejected) path.

## Lt/Lte Snapping Gap (NEW FINDING)

Audit confirmed: src/executor.rs:669-674 had NO bucket snapping for Lt/Lte.
Even sortAtUnix < T went straight to range_scan.

This is asymmetric to Gt/Gte which snap at lines 649-667.

Fix: Lt(field, T) → alive - bucket(duration=now-T) when field matches
the time-bucket field and duration is within 10% tolerance.

The complement approach (alive - bucket) is correct because:
- bucket(D) = items with timestamp in [now-D, now] (newer than threshold)
- Lt(T) where T≈now-D = items with timestamp < T (older than threshold)
- alive - bucket(D) = items NOT in the recent window = older items

## Risk Assessment

- Backwards compatible: max_range_scan_values defaults to None (no rejection)
- No sorted structures used: check is a HashMap::len() count only
- Lt/Lte snap is opt-in via time_buckets config (only fires for the one
  configured time-bucket field, same as Gt/Gte)
- No new locks: loaded_value_count() acquires existing RwLock briefly
