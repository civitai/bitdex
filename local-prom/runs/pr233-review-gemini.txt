### 1. Bit-exact equivalence with the slow path
* **[NIT] General Equivalence:** Confirmed. The fast path correctly mirrors the slow path's state mutations.
* **[NIT] Value present only in ops:** Confirmed. `result.entry(value).or_insert_with(RoaringBitmap::new).insert(bit)` correctly instantiates a new bitmap if it wasn't in the snapshot, matching `FilterOpCodec::apply`.
* **[NIT] Value present in snapshot, all bits removed:** Confirmed. `bm.remove(bit)` leaves an empty `RoaringBitmap` in the map, which matches the slow path's behavior of retaining empty bitmaps.
* **[NIT] ClearBit on a value not in snapshot:** Confirmed. `get_mut` returns `None`, so no insertion occurs.
* **[NIT] Wanted values that don't appear anywhere:** Confirmed. They are omitted from the resulting `HashMap`.

You can replace this with `bm.extend(bits)` (assuming `bits` is an iterable of `u32`), which is significantly faster as the `roaring` crate heavily optimizes bulk insertions.

### 2. Edge cases
* **[NIT] Header/Count Edge Cases:** Confirmed. `header.snapshot_len == 0`, `header.snapshot_len < 4`, and `count == 0` correctly skip the snapshot section and proceed to apply ops.
* **[NIT] Index bounds check:** Confirmed. An index entry extending past `snapshot_end` is correctly caught by the `abs_end > snapshot_end` check, returning `UnexpectedEof`.
* **[NIT] Wanted set edge cases:** Confirmed. An empty wanted set correctly short-circuits. Duplicate wanted values are correctly deduplicated via the `HashSet`.
* **[MAJOR] Corrupted Header OOM:** If a corrupted shard file has a massive `count` and a correspondingly massive `header.snapshot_len`, `count.checked_mul(16)` prevents integer overflow, but `vec![0u8; index_size]` could still attempt to allocate gigabytes of memory before failing the `read_exact` call. You should bound `header.snapshot_len` (or `index_size`) against `file.metadata()?.len()` to prevent out-of-memory panics on corrupted files.

### 3. Failure modes + fallback safety
* **[NIT] Fallback Safety:** Confirmed. Your reasoning is 100% correct. The partial fill during an indexed read is stored in a local `result` map inside `read_bucket_values_indexed`. If an error occurs, this local map is dropped. The fallback then reads the full bucket and inserts only the `wanted` keys into the outer `result`. Since buckets are disjoint by value, there is no risk of overwriting or corrupting entries from previously successful buckets.

### 4. Concurrency
* **[NIT] Lock Starvation:** Confirmed safe, net positive. `parking_lot::RwLock` prevents writer starvation, meaning a slow reader can block the compactor, which in turn blocks subsequent readers. Holding a read lock across blocking I/O (`File::open` and `read_exact`) is generally an anti-pattern for this reason. *However*, because this PR reduces the read time from ~380ms to ~1ms, it drastically *decreases* the lock hold time, significantly improving overall concurrency and reducing the chance of starvation compared to the status quo. No new deadlocks are introduced.

### 5. Performance follow-ups worth a separate PR
* **[NIT] `FileExt::seek_read` / `read_at`:** Highly recommended. Opening a new `File` handle on every read (especially on Windows) is expensive. Sharing a file handle and using positioned reads will yield further speedups.
* **[NIT] Ops section:** Since ops are append-only and unordered by value, scanning the entire tail is necessary. This is fine.
* **[NIT] Index buffer pooling:** Allocating `vec![0u8; index_size]` (up to 1.4MB for 89K values) on every query is a prime candidate for optimization. A buffer pool or memory-mapping (`mmap`) the index would eliminate this allocation overhead.

### 6. API surface
* **[NIT] Visibility Changes:** Lifting `shard_lock` and `is_valid_shard_file` to `pub(crate)` is perfectly fine and idiomatic for internal module access. A `with_read_lock<F>` helper would be slightly safer to prevent accidental guard leaks, but the current approach is standard and acceptable.

### 7. Microbench validity
* **[NIT] Confounds & Corroboration:**
  * **Confounds:** The speedup is currently bottlenecked by the `File::open` syscall (which is slow on Windows/NTFS). If the file handle were cached, the speedup would likely be even higher. Additionally, a warm page cache hides disk seek latency. On a cold cache with HDDs, random seeks could be slow, but the PR correctly mitigates this by sorting the offsets (`found.sort_by_key(|&(_, abs, _)| abs);`), ensuring sequential disk access.
  * **Corroborating measurements:** To confirm the win in production, look at P99 latency metrics for these specific queries, CPU profiling (expect `RoaringBitmap::deserialize_from` to vanish from the hot path), and memory allocation rates (which should drop proportionally).
